# 实操：从零建一个电商本体

跟着这份走一遍，你会得到一个**完整能用**的电商本体：4 个对象类型、3 个链接类型、8 个操作类型，
能跑通「下单 → 加购 → 支付 → 发货 → 收货」的完整链路。

分成 5 关，**每一关结束都有东西能跑**，不用等到最后才看到结果。全部手建大约 30 分钟。

> 想先看结果或者中途卡住：点顶部「本体规格 JSON」，把
> [`ecommerce.json`](./ecommerce.json) 的内容整个贴进去，点「应用这份 JSON」。
> 建议还是自己建一遍 —— 手指头记住的东西比眼睛看到的牢。

先点顶部的「**从零开始**」清空本体，切到「**01 本体建模**」。

## 为什么是这四个类型

先说结论，再动手。这个本体的核心是**订单行**（OrderLine）—— 也是唯一一个不那么显然的设计。

一张订单可以买多个商品，每个商品买几件、成交价多少，这些数据**既不属于订单，也不属于商品**，
它属于「这张订单和这个商品的这一次组合」。这种东西在关系库里是中间表，在本体里必须升格成**对象类型**。

判断标准就是那句话：**如果一个属性没法安放在任何一端，说明中间还缺一个对象类型。**

（顺带对比一下：演练场自带的那个咖啡供应链示例，我把订单简化成了「一单一商品」，
所以不需要订单行。你现在建的这个更接近真实电商。）

| | 是什么 | 为什么是对象类型而不是别的 |
|---|---|---|
| **Buyer 买家** | 下单的人 | 有身份，你会想搜他、点进他的页面看他所有订单 |
| **Product 商品** | 卖的东西 | 同上 |
| **Order 订单** | 一次购买行为 | 有状态、有生命周期、有操作作用在它身上 |
| **OrderLine 订单行** | 订单里的一行 | 承载「数量、成交单价」这些无处安放的属性 |

## 第 1 关：两个对象类型 + 两个操作

目标：能往本体里塞数据。

### 1.1 建 Buyer

左栏「对象类型」旁点 **+ 新建**。中间出现编辑器，填「基本信息」：

| 字段 | 填 |
|---|---|
| API 名 | `Buyer` |
| 中文名 | `买家` |
| 主键前缀 | `B` |

> 改完 API 名按 **回车** 或点空白处提交。API 名是机器用的标识（链接两端、操作参数、
> 实例主键引用的都是它），中文名只管显示。

「属性」区，新建的类型自带一个 `name` 属性，把它的中文名改成 `姓名`。然后用底部那行虚线框加另外三个：

| 中文名 | API 名 | 类型 |
|---|---|---|
| 手机 | `phone` | 文本 |
| 会员等级 | `level` | 枚举 |
| 城市 | `city` | 文本 |

`level` 加完后会多出一个逗号分隔的输入框，填：`普通，银卡，金卡`

最后把「标题属性」选成 **姓名** —— 这决定了列表和图谱里显示哪个字段。

### 1.2 建 Product

同样的流程：

| 字段 | 填 |
|---|---|
| API 名 | `Product`，中文名 `商品`，主键前缀 `P`，标题属性 `商品名` |

属性（自带的 `name` 改中文名为 `商品名`）：

| 中文名 | API 名 | 类型 |
|---|---|---|
| 商品名 | `name` | 文本 |
| SKU | `sku` | 文本 |
| 价格 | `price` | 金额 |
| 库存 | `stock` | 整数 |

### 1.3 用脚手架生成两个新建操作

**对象只能由 Action 创建** —— 这是本体唯一的写入口，没有「直接插一行数据」这回事。

选中 `Buyer`，右栏「脚手架」点 **生成「新建买家」操作**。再选中 `Product`，点 **生成「新建商品」操作**。

两下点击，两个可用的操作就有了。它们生成出来的就是普通操作类型 —— 不信可以点开看看，
参数和编辑都已经配好了，你随时能改。比如把「新建商品」的中文名改成「上架商品」更贴业务，
API 名 `createProduct` 保持不动就行。

右下角写入日志记下了它们。

## 第 2 关：订单 + 第一个手写 Action

### 2.1 建 Order

| 字段 | 填 |
|---|---|
| API 名 | `Order`，中文名 `订单`，主键前缀 `O`，标题属性 `订单号` |

属性：

| 中文名 | API 名 | 类型 | 备注 |
|---|---|---|---|
| 订单号 | `orderNo` | 文本 | |
| 状态 | `status` | 枚举 | `待支付，已支付，已发货，已完成，已取消` |
| 下单时间 | `placedAt` | 时间 | |
| 收货城市 | `shipTo` | 文本 | |
| 承运商 | `carrier` | 文本 | 发货时才填 |

### 2.2 建链接 placed

左栏「链接类型」点 **+ 新建**：

| 字段 | 填 |
|---|---|
| API 名 | `placed` |
| 起点 from | `Buyer` |
| 终点 to | `Order` |
| 基数 | `1 : N` |
| 正向 | `下的订单` |
| 反向 | `下单买家` |

基数读法：一个买家有 N 张订单，一张订单只有 1 个买家。
`1` 那一端是**真的会生效的约束** —— 后面你会看到它自动断开旧链接。

### 2.3 手写 createOrder

左栏「操作类型」点 **+ 新建**，API 名改成 `createOrder`，中文名 `下单`。

**① 参数**（点「+ 添加参数」两次）：

| 中文名 | 类型 | 补充 |
|---|---|---|
| 买家 | 对象引用 | 对象类型选 `Buyer` |
| 收货城市 | 文本 | |

> 参数的 API 名会自动生成（`p1`、`p2`），**创建后不可改** —— 规则和编辑都按它引用。
> 想要好看的名字，就在下面配规则之前先看清楚它叫什么。

**② 校验规则**：这个操作不需要，跳过。

**③ 写入编辑**（点「+ 添加编辑」两次）：

第一条，类型选 **新建对象**，对象类型选 `Order`。下面会列出 Order 的每个属性，逐个配：

| 属性 | 来源 | 值 |
|---|---|---|
| 订单号 | 主键 | —— 用刚生成的主键当订单号 |
| 状态 | 常量 | `待支付` |
| 下单时间 | 当前时间 | |
| 收货城市 | 参数 | 收货城市 |
| 承运商 | 常量 | 留空 |

第二条，类型选 **建立链接**：`买家` ──`placed`──▸ `新建的订单`

每条编辑下面会实时生成一句人话，对照着看有没有配错。

### ✅ 验收

切到运行模式，跑「下单」。图谱里出现一张 `O-1001`，用一条线连着买家。
点开订单详情，「关联对象」里能看到「下单买家」—— 反向也走得通。

## 第 3 关：订单行（核心）

### 3.1 建 OrderLine

| 字段 | 填 |
|---|---|
| API 名 | `OrderLine`，中文名 `订单行`，主键前缀 `L`，标题属性 `行号` |

属性：

| 中文名 | API 名 | 类型 |
|---|---|---|
| 行号 | `lineNo` | 文本 |
| 数量 | `qty` | 整数 |
| 成交单价 | `unitPrice` | 金额 |
| 小计 | `subtotal` | 金额 |

> **成交单价为什么要存？** 商品价格会变，但订单行必须冻结下单那一刻的价格 ——
> 这不是冗余，是业务事实。这类判断（哪些数据要快照、哪些要跟着源头走）是建模里最需要业务知识的部分。

### 3.2 两条链接

| API 名 | from | to | 基数 | 正向 | 反向 |
|---|---|---|---|---|---|
| `hasLine` | `Order` | `OrderLine` | `1 : N` | 订单行 | 所属订单 |
| `ofProduct` | `OrderLine` | `Product` | `N : 1` | 对应商品 | 相关订单行 |

注意 `ofProduct` 的方向：订单行**指向**商品。一个商品会被很多订单行引用，所以是 `N : 1`。

### 3.3 手写 addLine

新建操作，API 名 `addLine`，中文名 `加购商品`。

**① 参数**：

| 中文名 | 类型 | 补充 |
|---|---|---|
| 订单 | 对象引用 | `Order` |
| 商品 | 对象引用 | `Product` |
| 数量 | 数字 | 默认值 1 |

**② 校验规则**（三条，都是「属性比较」）：

| 左侧 | 运算符 | 右侧 |
|---|---|---|
| 属性 → 订单 → 状态 | 等于 | 常量 `待支付` |
| 参数 → 数量 | 大于等于 | 常量 `1` |
| 属性 → 商品 → 库存 | 大于等于 | 参数 → 数量 |

**③ 写入编辑**（四条）：

**新建对象** → `OrderLine`：

| 属性 | 来源 | 值 |
|---|---|---|
| 行号 | 主键 | |
| 数量 | 参数 | 数量 |
| 成交单价 | 属性 | 商品 → 价格 |
| 小计 | **计算** | 属性(商品→价格) **×** 参数(数量) |

**建立链接**：`订单` ──`hasLine`──▸ `新建的订单行`
**建立链接**：`新建的订单行` ──`ofProduct`──▸ `商品`
**修改属性**：`商品` 的 `库存` **减少** 参数 `数量`

### ✅ 验收

运行模式跑「加购商品」，给同一张订单加两次不同商品。你应该看到：

- 一次提交产生 **4 条编辑**，跨 3 个对象
- 图谱里订单挂出两条订单行，每条又指向各自的商品
- 商品库存被扣减
- 故意把数量填成 999，第三条规则立刻变红，提交按钮锁住

## 第 4 关：状态机

四个操作，都很短，但合起来订单才有生命周期。

### payOrder 支付

- 参数：订单（对象引用 → `Order`）
- 规则 1（属性比较）：订单.状态 等于 `待支付`
- 规则 2（**链接数量**）：`订单` 的 `hasLine` **正向** 数量 **大于等于** `1`
- 编辑：修改属性 → 订单.状态 **设为** `已支付`

规则 2 是这一关的重点：**空订单不能支付**。这种约束在关系库里得写触发器或应用层校验，
在本体里就是一条声明式规则。

### shipOrder 发货

- 参数：订单（`Order`）、承运商（**枚举**，选项 `顺丰，中通，京东物流`，默认 `顺丰`）
- 规则：订单.状态 等于 `已支付`
- 编辑 1：修改属性 → 订单.承运商 **设为** 参数 `承运商`
- 编辑 2：修改属性 → 订单.状态 **设为** `已发货`

> 把承运商放在订单上是个简化。如果一张订单可能**拆成多个包裹分批发货**，
> 运单就必须升格成独立对象类型 —— 判断标准还是那条：一个订单对多个运单，
> 运单号就没法安放在订单上了。演练场自带的示例里 `Shipment` 就是这么来的。

### completeOrder 确认收货

- 参数：订单
- 规则：订单.状态 等于 `已发货`
- 编辑：订单.状态 **设为** `已完成`

### cancelOrder 取消订单

- 参数：订单、原因（枚举 `买家取消，缺货，地址有误`）
- 规则（属性比较，运算符选 **属于**）：订单.状态 属于 `待支付，已支付`
- 编辑：订单.状态 **设为** `已取消`

### ✅ 验收

完整跑一遍：下单 → 加购 ×2 → 支付 → 发货 → 确认收货。
每一步之前试试跳步（比如没加购就支付、没支付就发货），看规则怎么拦住你。

**至此这个本体已经完整能用了。** 下面一关是加分。

## 第 5 关（加分）：双向遍历 + 删除

### removeLine 删除订单行

这个操作只有一个参数，但要摸到三个对象 —— 演示链接遍历在**规则**和**编辑**里都能用，而且方向可以相反。

- 参数：订单行（对象引用 → `OrderLine`）

**规则**（属性比较）：左侧来源选「属性」，目标下拉里选 **`订单行 的 所属订单`**（这是沿 `hasLine` 反向走一步），属性选 `状态`，等于常量 `待支付`。

> 已经支付的订单不许再删行 —— 而「订单状态」这个信息并不在参数里，是走出去拿的。

**编辑 1**（修改属性）：目标选 **`订单行 的 对应商品`**（沿 `ofProduct` 正向），
属性 `库存`，**增加**，值来源「属性」→ `订单行 → 数量`。把库存还回去。

**编辑 2**（删除对象）：目标 `订单行`。

删除对象时，挂在它身上的链接会一并断开 —— 撤销的时候又会一并接回来。

### 试试基数守卫

再建一个操作 `changeBuyer 改下单人`：

- 参数：订单（`Order`）、新买家（`Buyer`）
- 编辑：建立链接 `新买家` ──`placed`──▸ `订单`

跑一下。因为 `placed` 的基数是 `1 : N`（一张订单只能有一个买家），
你会在**编辑预览里看到一条你没有配的 `UNLINK`** —— 系统自动断开了旧的那条。

基数不是标注，是会执行的约束。

## 这个模型的边界

几个地方我是故意留着的，它们正好画出了简化模型和真实系统的分界：

**订单没有总金额。** 总金额 = 所有订单行小计之和，这是一个**聚合**。
真实 Foundry 里这是「派生属性」，由本体自己算；这个演练场没有实现派生属性，
所以我干脆不存 —— 存一个会算错的字段比不存更糟。你想看总额，点开订单沿 `hasLine` 走一遍就是。

**取消订单不退库存。** 退库存要遍历订单的**所有**行，而这个演练场的「走一步」只取第一个目标。
真实 Foundry 的 Action 可以对对象集合做批量编辑。所以这里退库存得一行一行走 `removeLine`。

**没有数据源。** 真实本体里对象类型要绑定后端数据集，做列 → 属性的映射，
实例是数据管道喂进来的。这个演练场跳过了那一层，所有实例都只能由 Action 创建。

这三条不是 bug，是简化。知道边界在哪，比假装没有边界更有用。

## 一页速查

**建完之后你的本体应该长这样：**

```
Buyer 买家 ──placed 1:N──▸ Order 订单 ──hasLine 1:N──▸ OrderLine 订单行
                                                            │
                                                    ofProduct N:1
                                                            ▼
                                                      Product 商品
```

**8 个操作：**

| 操作 | 教的是 |
|---|---|
| `createBuyer` / `createProduct` | 脚手架；对象只能由 Action 创建 |
| `createOrder` | 新建对象 + 建链接 |
| `addLine` | 关联实体、计算属性、一次写三个对象 |
| `payOrder` | 链接数量规则 |
| `shipOrder` | 枚举参数写进属性 |
| `completeOrder` / `cancelOrder` | 状态机、`属于` 运算符 |
| `removeLine` | 双向链接遍历 + 删除 |
