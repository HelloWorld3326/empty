01

泳道全景：九个模块，一条顺序

先看清楚自己要交付什么、每样东西「做完」的判定标准是什么。没有完成定义（DoD）的模块，都会在最后一周变成「还差一点」。

#模块工期依赖完成定义（可验证）
1仓库骨架与 CI1 天—两层目录建好；test_harness_boundary 能因为一次故意的反向 import 而变红；lint / type / test 三条 CI 全绿
2协议与数据模型2 天与算法共定DDL 迁移可跑；/mock/stream 能吐完整一轮假事件；前端用它跑通渲染
3流式桥接2.5 天模块 2断开重连带 Last-Event-ID 能续上；心跳 15s；订阅者落后能收到断档信号；单测覆盖这三条
4元数据与表卡片2 天数仓只读账号一条命令从库里抽出 N 张表的 YAML 卡片；人工补完口径后能被检索命中
5SQL 校验器1.5 天模块 4一组恶意 / 越界 SQL 用例全部被拒，一组正常查询全部通过——这组用例先写，再写实现
6SQL 执行器1.5 天模块 5超时能真的掐断正在跑的慢查询（不是等它跑完再报错）；行数上限生效；取消可用
7四个数据工具2 天模块 4/6 + Tool 契约四个工具能通过契约测试；返回内容在 token 预算内
8网关 · 认证 · 审计2 天模块 2/3未登录访问全部 401；每条 SQL（含被拒绝的）都能在 sql_audit 里查到
9评测与部署3 天模块 7一条命令跑完测试集出准确率；一条命令部署到演示环境
顺序的依据

模块 1→2→3 必须最先做完，因为它们解锁的是别人：模块 2 解锁前端，模块 2+3 解锁与算法的并行。剩下的 4→5→6→7 是你自己链条上的事，晚一天只影响你自己。先做解锁别人的，再做只影响自己的——三人小队里这条比任何优先级方法都管用。

02

与框架层联调：四道防线

「联调」不是某一天的事件，是一套从第一天就开始运转的机制。四道防线依次是：契约先行 → 双向假实现 → 契约测试 → 录制回放。每一道拦不住的问题，才轮到下一道。

防线 1 · D1–D3

契约先行：只有两处跨人接口，必须写成代码而不是文档

把 StreamBridge 收回自己手里之后，你和算法之间只剩两个接口。它们必须以「一个能 import 的 Python 模块」的形式存在——写在 Confluence 上的接口约定，两周后一定对不上。

# harness/dataagent/contracts.py —— 两人共同维护，改动需双方 approve

class RunManager(Protocol):
    async def start_run(self, thread_id: str, user_input: str,
                        run_id: str, ctx: RunContext) -> None: ...
    async def cancel(self, run_id: str) -> None: ...
    # 事件不从返回值出，而是由实现方 publish 到 StreamBridge

class Tool(Protocol):
    name: str
    description: str          # 给模型看的，算法可改，你不要动
    args_schema: type[BaseModel]
    async def run(self, ctx: ToolContext, **kwargs) -> ToolResult: ...

@dataclass
class ToolResult:
    ok: bool
    summary: str              # 进 prompt 的内容，必须受 token 预算约束
    artifact_ref: str | None  # 大结果走引用，不进 prompt
    error: str | None       # 失败时给模型看的错误，要可读、可自纠错

三条约定要在 D3 一起敲死：① 入参校验由框架层做（它有 args_schema），工具实现只管业务；② 工具失败不抛异常，返回 ok=False + 可读的 error，让模型自己纠错；③ summary 的 token 上限是多少（建议 1500），超了由工具自己截断并说明。

防线 2 · D3 起全程

双向假实现：两边都能在对方一行代码没写时跑通

这是整套机制里最值钱的一条。你写一个假的框架层，算法写一组假的工具，两个假实现都遵守防线 1 的同一份契约。

你写：FakeRunManager

不调模型，按脚本发一串预设事件（文本增量 → 工具调用 → 结果 → 结束）。有了它，你的网关、流式桥接、前端可以在 D3 就完整跑通，不等算法。

算法写：FakeTools

四个工具的假版本，返回固定的假表卡片、假 schema、假结果集。有了它，他的循环可以在你的执行器没写完时就跑通，也不等你。

关键约束

两个假实现必须和真实现跑同一套契约测试（防线 3）。否则「各自跑通、合起来炸」照样会发生，只是炸得更晚。

# app/testing/fake_runtime.py —— 你写，D3 交付
class FakeRunManager:
    def __init__(self, bridge: StreamBridge, script: str = "happy_path"): ...

    async def start_run(self, thread_id, user_input, run_id, ctx):
        for ev in load_script(self.script):   # YAML 脚本，一行一个事件
            await asyncio.sleep(ev.delay)      # 模拟真实节奏，能暴露前端时序 bug
            await self.bridge.publish(run_id, ev.event, ev.data)
        await self.bridge.publish_end(run_id)

# 至少准备四个脚本，覆盖前端和网关必须处理的四种情况：
#   happy_path        正常一轮
#   tool_error        工具失败 → 模型自纠错 → 第二次成功
#   clarification     反问用户，中断等待
#   run_error         模型超时，终态是 error
防线 3 · D4 起，每次 PR

契约测试：同一套断言，跑在真假两个实现上

放在 tests/contract/，两人共同维护。它不测业务逻辑，只测契约——参数化跑过每一个实现。假实现和真实现的行为一旦分叉，CI 立刻红。

# tests/contract/test_tool_contract.py
@pytest.mark.parametrize("tool", [FakeSearchTables(), SearchTables(db)])
async def test_bad_args_returns_error_not_raise(tool):
    r = await tool.run(ctx, query=None)
    assert r.ok is False and r.error          # 约定②：不抛异常

@pytest.mark.parametrize("tool", ALL_TOOLS)
async def test_summary_within_token_budget(tool):
    r = await tool.run(ctx, **tool.sample_args)
    assert count_tokens(r.summary) <= 1500     # 约定③

这套测试由谁写？建议 D3 你和算法各写一半、互相 review。它是唯一能在 D10 之前就发现语义分歧的东西，值得两个人各花半天。

防线 4 · D10 起

录制回放：把一次真实的 run 冻成 fixture

D10 集成成功当天，立刻把那一轮的完整事件序列录成 JSON 存进仓库。之后：前端的测试用它、你的网关测试用它、回归也用它。谁都不需要真模型、不需要真数据库，就能验证「事件流没被改坏」。

成本约 2 小时，收益是后面十天里每一次「前端说事件不对、后端说我没改」的扯皮都能在 30 秒内定论。

改 contracts.py 的人，必须在同一个 PR 里同时改：真实现、假实现、契约测试。PR 需要另一个人 approve。不允许「我先改了，你回头跟一下」——那句话是三人小队里所有集成事故的开头。

三十分钟，三步：① 你把 FakeRunManager 接上真网关，前端点一次提问，看事件在浏览器里长什么样，截图发群里。② 算法把 FakeTools 接上真循环，跑一次，把他侧产生的事件序列打印出来发群里。③ 两份序列并排比对——事件名对不对得上、字段名一致不一致、工具调用的 id 是谁生成的。90% 的集成事故在这一步就能看出来，而此刻距离 D10 还有三天，改得动。

04

技术要点：六件容易做错的事

1 · 元数据抽取的三个坑

  • 注释拿不到不是异常，是常态。覆盖率 80% 意味着有 20% 空白，抽取器要把「无注释」显式标成待补状态，而不是留空字符串——待补清单就是人工校对的工作单。
  • 采样值要脱敏再入卡片。示例值对模型理解字段极有帮助，但手机号、姓名不能进 YAML（YAML 是要进 Git 的）。规则：字符串列采样时做长度与字符类型检测，疑似敏感的只写「格式示例」不写真值。
  • 分区列必须单独标记。数仓表的分区列决定了 SQL 写得对不对（见第 6 点），它不是一个普通字段。

2 · 表卡片长什么样

table: dwd_order_detail
datasource: dw_main
display_name: 订单明细表
domain: 交易
purpose: 每行一笔订单中的一个商品，交易分析的主表
grain: 订单 × 商品                  # 粒度写错，聚合就一定错
time_column: dt
metrics_note: |                     # 这一段的价值大于其余全部字段之和
  GMV = pay_amount 求和，含税、不扣退款
  按天统计一律用分区列 dt，不要用 create_time
columns:
  - {name: order_id,   type: bigint,         cn: 订单号,           sample: "8801234"}
  - {name: pay_amount, type: decimal(18,2),  cn: 支付金额（含税）,  sample: "129.00"}
  - {name: dt,         type: string,         cn: 分区日期,         sample: "2026-08-24", partition: true}
  - {name: user_id,    type: bigint,         cn: 用户ID,           todo: "口径待确认"}
related:
  - dim_user  # dwd_order_detail.user_id = dim_user.user_id
allowed_roles: ["*"]

3 · SQL 校验器必须拒绝的七类

#拒绝什么说明
1根节点不是 SELECTINSERT / UPDATE / DELETE / DDL / CALL 一律拒
2多语句分号拼接的第二条语句
3数据修改型 CTEPostgreSQL 允许 WITH x AS (DELETE FROM t RETURNING *) SELECT * FROM x——根节点是 SELECT，却会删数据。只看根节点类型的校验器在这里全军覆没，必须遍历整棵 AST
4SELECT ... INTO 类含 INTO OUTFILE / INTO DUMPFILE
5文件与系统函数pg_read_file / pg_ls_dir / lo_import / LOAD_FILE 等
6表不在白名单遍历 AST 收集全部表引用，含 CTE 内部与嵌套子查询
7缺 LIMIT 或超上限这一类不拒绝，而是改写：注入 LIMIT，或把过大的 LIMIT 收紧到上限

只读账号是第一道防线，AST 校验是第二道。两道都要，别只靠一道——AST 挡不住你没想到的语法，只读账号挡不住把数仓拖垮的全表扫描。

4 · 超时必须由数据库执行，不能靠 Python

这是最常见的错误实现：用 asyncio.wait_for 包住查询，超时就抛异常。问题是 Python 只是放弃了等待，数据库那边的慢查询还在跑，继续占着数仓资源——演示当天并发几个人，数仓就被你们拖垮了。正确做法各引擎不同：

引擎设超时强制终止
PostgreSQL事务内 SET LOCAL statement_timeout = '30s'驱动的连接取消机制（另开控制连接发 cancel 请求）
MySQL优化器提示 SELECT /*+ MAX_EXECUTION_TIME(30000) */ …，或会话级 MAX_EXECUTION_TIME（仅对只读 SELECT 生效）另开一条连接执行 KILL QUERY <thread_id>，所以要记住每条查询的连接 id

行数上限同样要两层：SQL 里注入 LIMIT 是第一层，游标侧 fetchmany 到上限就停是第二层——防止某些引擎对 LIMIT 的处理不如你预期。

5 · 工具返回的 token 预算

工具进 prompt 上限超了怎么办
search_tables≈ 600 token只返回 5–8 张卡片的摘要（表名 + 中文名 + 一句话用途），绝不返回字段
describe_table≈ 1500 token宽表截断：优先给分区列、时间列、主键、与问题词面匹配的字段，再补到 30 个，并注明「已截断，共 N 字段」
search_knowledge≈ 1200 token最多 5 段，每段截断并带出处
run_sql≈ 1500 token进 prompt 最多 50 行 × 20 列，单元格截断 100 字符；完整结果走 artifact_ref，前端另取

再加一条 run 级总量告警：单轮问答超过 3 万 token 就打日志。它是「上下文设计出问题了」的最早信号。

6 · 评测脚本的最小形态

判定分三档，都能自动算，而三档的比例告诉你该去修哪里：

档位含义这一档偏多说明什么
A结果集与标准 SQL 的执行结果一致—
B结果不一致，但用到的表是对的检索对了、SQL 写错了 → 提示词与口径问题，找算法
C找错表，或直接报错元数据问题 → 表卡片没写清楚，找你自己

这个划分的用处是止住互相甩锅：B 多就是提示词的事，C 多就是表卡片的事，不需要开会讨论。

05

五个必炸点

按「会浪费你多少小时」排序。前三个我见过太多次，值得在写代码之前就先记住。

#现象真正原因预防
1超时了，但数仓还是被拖垮asyncio.wait_for 只放弃等待，数据库那边的查询还在跑用引擎自己的超时机制（见 04-4）。写执行器的第一天就写对，事后很难发现
2前端「卡住半天，然后内容一次性全出来」SSE 被 Nginx / Ingress 缓冲了，不是你的代码问题响应头加 X-Accel-Buffering: no；Ingress 上关掉 proxy buffering。D17 部署时才会暴露，但要在 D3 写进协议文档

06

需要你澄清的五件事

前三个会改变上面的实施细节，后两个会改变联调机制或效率。都不阻塞——我按推荐先写着。

Q1 · PostgreSQL 和 MySQL，先打通哪一个？

范围削减清单第 1 项要求 MVP 只做一个引擎。这直接影响执行器怎么写（两者的超时与强杀机制完全不同，见 04-4），也影响校验器的重点（数据修改型 CTE 是 PostgreSQL 独有的坑）。

推荐：选数据部门真实查询量最大的那个，不是选技术上更顺手的那个。测试集要从它的历史查询日志里挖。
Q2 · 单仓还是两个仓？分支与 review 怎么定？

这决定契约测试能不能在一次 CI 里同时跑真假两个实现——也就是防线 3 成不成立。两个仓的话，框架层要发版、应用层要升版本，改一次契约要走两轮发布，三人小队扛不住这个开销。

推荐：单仓（monorepo），两层用目录隔离 + CI 强制单向依赖，效果与两个仓一样但零发布开销。主干开发 + 短分支，PR 必须另一人 approve，改 contracts.py 的 PR 必须两人都看。
Q3 · 有没有可用的 CI 环境？能跑容器吗？

防线 3 和防线 4 都依赖「每次 PR 自动跑契约测试与回放测试」。如果没有 CI，这两道防线退化成「记得手动跑」，也就等于没有。

推荐：D1 就确认。若公司 CI 不可用，退而求其次用 pre-commit hook + 每天早上一次手动全量跑，并把这条写进团队约定——但要知道这是明显更弱的保障。
Q4 · 算法同学愿意承担 FakeTools 和一半契约测试吗？

大约 1 人天。这是防线 2 和 3 的前提。从算法的视角看，这是「给别人写的测试代码」，很容易被排到最后然后不了了之——但它恰恰是让他自己能在 D5–D9 独立开发的东西。

推荐：D1 就把这件事作为他的交付物写进分工，而不是作为「有空就做」。跟他讲清楚收益：有了 FakeTools，他到 D10 之前完全不用等你的执行器。
Q5 · 本地能直连数仓吗，还是必须跳板机？

这条对开发效率的影响可能超过其余所有因素之和。如果每次调试 SQL 都要过跳板机、不能在本地跑集成测试，模块 4–7 的实际耗时要在估算上乘 1.5。

推荐：优先争取一个脱敏的测试库放在能直连的网络里，结构与生产一致、数据量小。拿不到的话，D1 就要把这个约束反映到排期上——而不是等到 D8 发现调不动。
