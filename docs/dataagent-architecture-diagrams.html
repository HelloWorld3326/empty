数据 Agent 平台架构图

三张图分别回答三个不同的问题：系统由哪些部件构成并如何互相调用；产品对用户提供哪些能力、分几期交付；一次问答在系统内部实际怎么流转。配合《架构蓝图与 MVP 交付计划》使用。

01

技术架构图

六层自上而下，箭头标注请求下行的每一跳；右侧是流式事件的上行链路；底部虚线框是不在请求链路上、但贯穿全部层次的横切关注点。

读这张图的四个要点

为什么框架层要单列

框架层与数据业务完全无关，可独立发布与升级。这一刀切下去，未来做别的业务智能体时可以整体复用；不切，三个月后编排代码里会长满 SQL 相关的判断。

为什么工具是一层而不是模块

元数据、检索、SQL、可视化、沙箱、外部协议共用同一套注册与调用契约。它们是平行可插拔的，任何一个下线不影响其余——这是能力可增量交付的前提。

为什么 SSE 上行要单独画

它不是「响应」，而是一条与请求链路方向相反、贯穿全程的独立通道。文本增量、工具状态、有界快照都走它。前端的复杂度几乎全部来自这条线。

为什么横切关注点画成虚线

配置、可观测、安全、发布不在任何一次请求的路径上，但每一层都要用。画进主链路会让人误以为它们是调用环节。

02

产品架构图

从使用者往下拆到底层依赖。场景与平台能力按交付阶段用线型区分——这张图同时也是产品路线图。

阶段划分的依据

阶段交付什么为什么排在这个位置
MVP自助取数问答、元数据问答、智能体编排、工具体系、评测与反馈取数与元数据问答共用同一套检索与上下文，边际成本最低；评测放进 MVP 不是为了好看，是为了第一周就能看见准确率曲线
一期分析报告、看板沉淀、知识与记忆、安全与权限「知识与记忆」承载样本飞轮，是准确率的第二台阶；用户一多，权限立刻从可选变成阻塞
二期数据质量、血缘、开发助手、主动洞察、成本配额这些依赖更完整的元数据（尤其血缘），在资产层足够厚之前做，效果撑不起来
03

运行时序：一次问答怎么跑

前两张图是静态结构，这张是动态机制。评审时被追问最多的往往是这一张——尤其是「模型到底自己决定什么」和「出错了怎么办」。

图上没画但必须存在的两个约束

轮次上限：循环必须有硬上限，否则模型可能在「搜表→查口径→再搜表」之间空转直到烧完 token。每次 SQL 落审计：包括被校验器拒绝、根本没执行的那些——它们恰恰是安全复盘时最需要看的记录。

04

需要和你澄清的四件事

这两张图我按目前谈定的信息画了，但下面四点会改变图的内容或呈现方式。都不阻塞，先按推荐画着，你定了我再改。

Q1 · 这两张图给谁看？

对内技术评审、对外向领导汇报、还是放进立项材料？技术架构图现在带了具体技术名词（PostgreSQL、K8s、阿里云百炼）。如果是给非技术领导看，这些应该抽象成「平台库 / 容器平台 / 大模型服务」。

推荐：保留现在这版做技术评审用；如果要对上汇报，我再出一版去掉技术选型名词的产品视角图。
Q2 · 阶段标注要不要保留在产品架构图上？

现在场景层和能力层带了 MVP / 一期 / 二期的线型区分。好处是一张图同时讲清「做什么」和「什么时候做」；风险是对外汇报时等于公开承诺了排期，后面调整会被追问。

推荐：内部版保留，对外版去掉阶段标注只留能力全景。需要的话我出两版。
Q3 · 需要什么交付格式？

现在是网页内嵌的矢量图，可以直接截图，缩放不糊。如果要放进 PPT 或 Visio 再编辑，我可以另外导出独立的 SVG 文件（可在 Illustrator / Figma / Visio 里拆开改），或者出 Mermaid / PlantUML 源码让你们自己维护。

推荐：独立 SVG 文件 + 仓库里留一份生成脚本，图要改时改脚本重生成，不用手工挪框。
Q4 · 产品架构图的使用者层对不对？

我按「数据分析师 / 数据工程师 / 业务方 / 数据治理岗」四类画的，这是从「给数据部门做数据治理与分析」推出来的。如果实际上业务方在可见的未来都不会直接使用（只有数据部门内部用），这一层要收窄——它会连带影响权限模型的优先级（图 2 里「安全与权限」现在排在一期）。

推荐：先确认业务方是否是明确的目标用户。若否，使用者层收成三类，权限相关工作可以整体后移。
