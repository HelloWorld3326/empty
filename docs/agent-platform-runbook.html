SUPCON 数据智能体平台 · 一期

启动手册

第一周逐日操作、五个人怎么并行、以及第二周之后每个人的工作循环。配套《一期技术方案与任务拆解》使用。

§01

先纠正一个思路

很多人会这样规划：部署数据库 → 建表 → 写后端 → 写前端。

这个顺序不能说错，但它是串行的——第一步没做完，后面四个人只能等。五个人的项目按这个节奏走，第一周实际只有一个人在产出。

第一周不写任何业务代码，写的是「让五个人能同时干活的地基」。

目标不是"做出功能"，而是让第二周开始，五个人可以完全不互相等待地并行工作。

这个地基包含三样东西，缺一样就会有人卡住：

地基不铺好谁被卡住铺好要多久
能跑起来的数据库 + 建好的表两个后端、算法半天
写死的接口定义（OpenAPI）所有人2 天
基于接口定义的假数据服务（mock）前端1 天

关键在于：地基里最贵的不是数据库，是接口定义。数据库半天就起来了，但"这个接口叫什么、传什么、返回什么"如果不先说死，五个人就会各写各的，第三周拼起来的时候全是对不上的字段。

§02

Day 0 · 半天 · 1 个人

这是唯一必须串行的半天。BE1 一个人做完，其他人 clone 下来就能跑。

D0铺地基BE1 · 半天

1 · 建仓库，定目录

mkdir agent-platform && cd agent-platform
git init
mkdir -p contracts/mock backend agent-runtime frontend deploy var/attachments
目录放什么
contracts/建表语句、接口定义、SSE 协议 —— 唯一真源
backend/FastAPI 业务后端
agent-runtime/Agent 执行内核（独立包）
frontend/Vue3 前端
deploy/docker-compose、部署脚本

2 · 拉起数据库和 Redis

把仓库里的 docs/starter/docker-compose.yml 复制到 deploy/，然后：

cd deploy && docker compose up -d
docker compose ps          # 两个容器都是 healthy 就对了

这就是你说的"部署 PG 和 Redis"——用 Docker 的话是一条命令、五分钟的事，不需要专门排期。

3 · 环境变量

复制 docs/starter/.env.example 成根目录的 .env，各人填自己的值。.env 必须写进 .gitignore，永远不提交。

4 · 项目约定

把 docs/starter/CLAUDE.md.template 复制成根目录的 CLAUDE.md（用 Codex 的人再复制一份 AGENTS.md）。这份文件 AI 会自动读，它决定了 AI 生成的代码符不符合你们的规矩。

5 · 推第一个提交

git add -A && git commit -m "chore: 项目骨架与本地开发环境"
git push -u origin main
Day 0 验收　任何一个组员执行 git clone → cd deploy && docker compose up -d，两个容器 healthy。
到此为止，基础设施这件事就结束了，整个一期不用再管。
§03

第一周 · 逐日

D1Kickoff + 五路开工全员

上午 · Kickoff 会（1 小时，必须开）

不是走过场。要当场对齐三件事：

  1. 过一遍决策台账（技术方案第 1 节的 18 条）。逐条念，谁有异议现在提。会后这 18 条就是不可推翻的前提。
  2. 讲清楚"垂直切片"分工法：一个人从表到接口到页面把一个切片做完，不要按层分工。当场把 S0–S24 分掉。
  3. 当场认领三个外部依赖的 owner：谁去盘点内网 MCP Server（R3）、谁去要知识库接口文档（R1）、谁去申请 +1 前端（R2）。
BE1写 contracts/schema.sql 前半：身份权限 4 张表 + 智能体域 5 张表　产出 9 张表 DDL，本地能跑通
BE2写 contracts/openapi.yaml 骨架：65 个接口的路径和方法先列全，请求响应体留空　产出 能被工具解析的 yaml
AL写几十行脚本直接调百炼 OpenAI 兼容端点，验证 function calling　产出 终端能看到模型返回 tool_calls
FE1pnpm create vite 起 Vue3+TS，装 Pinia / AntDV，配路由和布局壳子　产出 浏览器能打开，导航在
FE2组件基建：表格封装（分页/搜索/选择列）、弹窗封装、表单封装　产出 三个能用假数据渲染的组件
AL 今天这个脚本是整个项目风险最高的一次验证。如果百炼的 function calling 跟预期不一样，agent 运行时的做法要改——今天发现只损失一天，第三周发现就要命了。
D2表建起来、接口补肉
BE1补完资源域 5 张表 + 会话运行域 7 张表；写 seed.sql（角色权限、默认管理员、默认组）；跑通建库
BE2给每个接口补请求体与响应体 schema，先补 agents / resources 两组
AL把昨天的脚本扩展成能流式输出：模型回答一个字一个字打印出来
FE1接入请求层（axios 封装、错误处理、loading 态），先连写死的 JSON 跑通
FE2继续组件基建；开始做流式渲染组件原型（先用 setInterval 假装有字流进来）
Day 2 验收 
docker compose exec postgres psql -U agent -d agent_platform -c "\dt"
# 应该看到 20 张表
docker compose exec postgres psql -U agent -d agent_platform -c "select * from sys_user;"
# 应该看到 seed 进去的默认管理员
这就是你说的"执行 DDL 把表建好"——它确实要早做，因为表结构是所有人的共同语言：后端照着它写查询、前端照着它理解字段、AI 照着它生成代码。但它只值 1.5 天，不是一周。
D3SSE 协议定稿 + 假服务上线最关键的一天
三人会AL + BE2 + FE2 上午开 1 小时，定稿 contracts/sse-protocol.md：9 类事件字段全部写死 + 一段完整运行的示例事件流
BE2用 FastAPI 写一个假的 SSE 服务：不接大模型，按示例事件流定时吐假数据（每 200ms 一个 message.delta）。几十行代码
AL搭 agent-runtime 骨架，把流式脚本改造成能发出这 9 类事件
FE2把流式渲染组件接到假 SSE 服务——浏览器里能看到思考过程展开、字往外蹦、引用条数累加
BE1补完 conversations / runs / records 三组接口定义
FE1跑通 mock server：用 Prism 或 msw 从 openapi.yaml 自动生成假接口，所有列表页拉到假数据
Day 3 验收 · 第一周最重要的一次

前端在浏览器里，在后端一行业务代码都没写的情况下，能看到一个假的智能体在流式回答问题，思考过程在展开，引用来源在累加。

到这一刻，前端就彻底解绑了——接下来两周它不需要等任何人。

D4类型生成 + CI + 错误码
BE1写 contracts/errors.md 统一错误码；配 CI（lint + 测试 + 校验 openapi.yaml 合法）
BE2后端接入 spec：生成 Pydantic model，路由骨架全部建好（函数体先 raise NotImplementedError）
ALagent-runtime 骨架 + 单测框架，能跑通"输入一句话，输出 9 类事件"
FE1前端接入 spec：生成 TS 类型和 API 客户端到 src/api/，所有页面改用生成的类型
FE2继续组件库，把 Day 3 的流式组件收拾成可复用的
为什么类型生成这么重要：这是防 AI 幻觉的核心护栏。AI 写代码最常见的错就是字段名编错——后端叫 agentId，前端 AI 写成 agent_id，运行时才发现是 undefined。用生成的类型之后，编译期就红了，根本提交不上去。
D5验收 + 分配第二周
W1 验收演示（半小时，全员在场）　按这五条逐一演示，做不到就不算过：
  1. 新人 clone → docker compose up -d → 20 张表建好、默认管理员在
  2. openapi.yaml 里 65 个接口全部有完整定义，能用 Swagger UI 打开浏览
  3. mock server 跑起来，前端所有列表页有假数据
  4. 前端能连上假 SSE 服务，看到完整的流式回答动画
  5. 前后端的类型都是从 spec 生成的，不是手写的
下午：按任务表把 W2 的活分到人，每个人拿到的是一张「切片任务卡」（模板见仓库 docs/starter/切片任务卡示例.md）。
§04

第二周之后 · 每个人的工作循环

第一周之后节奏就固定了，每个人循环做这四件事：

01

领一张切片任务卡

上面写清楚四件事：切片范围、已定的契约、验收标准、不许动什么。

02

整段贴给 AI

让它把这个切片从 service、路由、页面到测试一次做完。契约写死了，AI 不会编字段名；划了边界，AI 不会去改别人的文件。

03

自己 review

权限有没有漏、有没有 N+1 查询、外部调用有没有超时处理、测试测的是行为还是实现。看不懂的代码不许合。

04

跑通验收，提 PR

验收标准里的每一条都真的点一遍，包括异常情况。

AI 提速的边界要有心理准备。AI 让"敲代码"快 2.5–3 倍，但"想清楚要什么、跟别人对齐、拿到内网权限、验收异常路径"这些一点没变快。

所以任务卡写得越清楚，AI 的产出越高——你花在写任务卡上的 20 分钟，能省 AI 两小时的返工。

任务卡为什么必须有这四个部分

AI 写代码的失败模式不是"写不出来"，是在你没说清的地方自己编一个。编出来的东西单看没问题，跟别人的代码一拼就对不上。这四个部分正好堵住四个编造的入口：

缺了什么AI 会怎么翻车
切片范围顺手把相邻功能也做了，或者只做一半
已定的契约自己发明字段名和接口路径
验收标准只写 happy path，异常分支全是 pass
不许动什么去改公共文件，把别人的活覆盖掉
§05

每周固定动作

时间动作时长
每天早上站会：昨天做完什么、今天做什么、被谁卡住10 分钟
每周一契约对齐会：过一遍这周 contracts/ 的改动，有没有人的代码要跟着改30 分钟
每周五里程碑验收：按周计划的判定标准逐条演示30 分钟

四道里程碑闸门

时点代号判定标准
W2 末M1创建 agent → 即时测试 → 看到流式回答（工具用 mock）
W3 末M2agent 能真调 MCP 工具、真查知识库；发布 / 上下架闭环
W4 末M3功能完整，happy path 全通
W5 末M4可交给业务专家试用

M1 是最关键的一道闸。如果 W2 末"创建 agent → 即时测试 → 流式回答"这条最短链路没通，不要继续往下堆功能——先停下来查为什么，因为后面所有东西都挂在这条链路上。
