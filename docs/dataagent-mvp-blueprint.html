值得照抄的架构决策

  • Harness / App 两层单向依赖，用 CI 测试强制（test_harness_boundary.py）。这是让「框架」不被业务代码腐蚀的唯一有效手段。
  • ThreadState 作为唯一状态载体，扩展自 LangGraph 的 AgentState，承载 sandbox / artifacts / todos / title 等。所有中间件读写同一个对象。
  • Middleware chain：把「模型调用前要做的事」拆成可插拔的有序段，而不是塞进一个巨型函数。
  • 工具三源合并：内置、配置化、MCP 三类工具由 get_available_tools() 统一装配。
  • SSE 双通道：既发 per-chunk 增量，也发有界的 values 快照——增量丢了还能靠快照对齐。
  • 配置分权：会导致代码 import 的 plugins: 只能写在运维掌管的 config.yaml，绝不放进 API 可写的 extensions_config.json。
  • 回环默认绑定：只有 nginx 对外，且 CI 校验所有 compose 端口都带显式 bind 地址。
为什么不 fork

15 万行非测试后端代码，团队栈熟悉度「一般」，LangGraph 无人接触过，有效人力约 2.5 人月。fork 后要先读懂再删——而它的 authz / middleware / persistence 互相咬合，删一块塌一片。更关键的是：换 Vue 已经废掉它 6 万行前端，保留后端的唯一理由只剩「以后 merge 上游」，而你们必然要改核心（加 SQL 执行器、数据工具），这个理由随即失效。真正值得复用的是上面这七条架构决策，读文档和关键文件就能拿到，不需要背 15 万行代码。

Agent 的六个工具

MVP 只有一个 lead agent，它能调用的工具就是产品能力的全集。工具越少、边界越清楚，ReAct 循环越稳。

工具签名职责与约束
search_tables(query: str, top_k=8)在表卡片上做检索，返回候选表的摘要卡片（表名/中文名/业务域/一句话用途）。只在白名单内检索
describe_table(table: str)返回完整 schema：字段名、类型、中文注释、示例值、常用口径、关联表提示
search_knowledge(query: str, top_k=5)转发到公司向量库 API，返回口径文档片段 + 出处，供引用
run_sql(sql: str, datasource: str)校验 → 限流 → 执行 → 返回结果集。SELECT-only、白名单表校验、强制 LIMIT、语句超时、行数上限，全程审计
make_chart(spec: ChartSpec)只产出图表配置 JSON（类型 + x/y 字段 + 标题），不渲染、不跑代码，前端 ECharts 负责画
ask_clarification(question: str)口径歧义或缺少时间范围时反问用户，中断本轮等待输入
这一节最容易被忽略的设计

search_tables 与 describe_table 必须分成两个工具，不能合并成一个「给我所有表结构」。白名单 200 张表的完整 schema 塞进 prompt 会是几万 token，成本高且准确率反而下降。正确的形状是：先检索出 5–8 张候选表的摘要，agent 判断后只对 1–3 张展开完整结构。这是 Text-to-SQL 准确率和成本的关键分水岭。

部署形态

  • K8s Deployment replicas=1 + strategy: Recreate。单 Pod 内 uvicorn 多 worker 关闭（agent 状态在进程内），并发靠 asyncio。
  • 启动时把上次遗留的 running 运行标记为 interrupted，前端展示「已中断，可重试」。不做 checkpoint 续跑——取数问答是短任务，重试成本低于实现成本。
  • 配置：config.yaml 走 ConfigMap，数据源凭证与模型 API Key 走 Secret。
  • 前端静态产物由同一个 Pod 的 nginx sidecar 托管，或直接打进镜像——不为 MVP 单独开一个前端服务。

核心数据模型与 SSE 协议

这两样东西必须在 D4 之前冻结。它们是前后端并行开发的唯一前提，也是未来「换回官方前端」这条退路能否保留的关键。

数据模型

前五张表的语义刻意对齐 DeerFlow；后五张是本项目独有的数据侧资产。

-- 对齐 DeerFlow 语义的五张核心表 --------------------------------
users        (id, username UNIQUE, password_hash, display_name, role, is_active, created_at)
threads      (id, user_id, title, created_at, updated_at, archived_at)
messages     (id, thread_id, role, content, created_at, seq)
             -- role: user | assistant | tool | system
runs         (id, thread_id, status, model, started_at, finished_at, error,
              input_tokens, output_tokens)
             -- status: queued | running | succeeded | failed | interrupted | cancelled
tool_calls   (id, run_id, message_id, tool_name, args JSONB, result JSONB,
              status, started_at, finished_at, error)
artifacts    (id, thread_id, run_id, kind, uri, meta JSONB, created_at)
             -- kind: table | chart | csv

-- 数据侧资产 --------------------------------------------------
datasources  (id, name, engine, dsn_secret_ref, is_active)
             -- engine: postgres | mysql   (starrocks 留给完整版)
table_cards  (id, datasource_id, schema_name, table_name, display_name_cn,
              business_domain, purpose, columns JSONB, sample_values JSONB,
              metrics_note, embedding_ref, reviewed_by, reviewed_at,
              allowed_roles TEXT[] DEFAULT '{*}')
             -- columns: [{name,type,comment_cn,nullable,is_sensitive}]
sql_audit    (id, user_id, thread_id, run_id, datasource_id, question,
              generated_sql, validated BOOL, reject_reason, executed BOOL,
              row_count, elapsed_ms, created_at)
qa_samples   (id, thread_id, question, final_sql, tables_used TEXT[],
              user_feedback, created_at)
             -- MVP 只写不读；完整版接成 few-shot 检索
为什么 sql_audit 单独成表

它不是 tool_calls 的冗余。tool_calls 服务于会话回放，字段随工具协议演化；sql_audit 服务于安全合规，字段必须稳定、必须能被 DBA 和安全团队直接查询、必须记录被拒绝的 SQL（那些根本没进 tool_calls）。这张表是你面对合规质疑时唯一的挡箭牌，成本极低。

SSE 事件协议

单一 GET /api/threads/{tid}/runs/{rid}/stream，text/event-stream。事件名与 DeerFlow 的语义对齐，字段收敛到最小集。

run.started        { run_id, thread_id, model }
message.delta      { message_id, delta }              # 助手文本增量
tool_call.started  { tool_call_id, tool_name, args }
tool_call.delta    { tool_call_id, stage, detail }     # 如 stage=validating|executing
tool_call.finished { tool_call_id, status, result_ref }
artifact.created   { artifact_id, kind, uri, meta }
state.snapshot     { messages_tail, tool_calls_open }  # 有界快照，每 N 秒一次
run.finished       { run_id, status, usage }
run.error          { run_id, code, message }
ping               { ts }                             # 15s 心跳，防中间层断流
  • 快照 + 增量双通道照抄 DeerFlow：增量丢包时前端可用 state.snapshot 对齐，不必重连整轮。
  • result_ref 而非内联结果：大结果集走 GET /api/artifacts/{id} 分页取，避免把上万行塞进 SSE。
  • 断线重连带 Last-Event-ID，服务端从 messages.seq 续发。
D3 必须交付

这份协议 + 上面的 DDL + 一个能吐假事件的 /mock/stream 端点。前端从 D4 起就靠 mock 流开发，不等后端。这是整个排期里最重要的一次解耦——没有它，前端会空转到第二周。

关键路径

下面这条链上任何一环延期，演示日直接顺延——它上面没有缓冲：

D3 SSE 协议冻结 ─→ D7 编排引擎可跑 ─→ D9 端到端贯通 ─→ D12 主线可演示 ─→ D16 功能冻结 ─→ D20 演示
     ↑ 你                ↑ 你               ↑ 全员            ↑ 你+A           ↑ 你

五个环节里四个在你手上。这是「核心你来写」的必然结果，也是这份排期最大的单点风险——见第 8 节 R4。

排期里刻意留出的三个缓冲

① 第 4 周有 4 天不排新功能，这是唯一的总缓冲，不要提前花掉。② 后端 B 的泳道全部是可独立交付的模块，人力不足时整条延后不影响主线。③ 白名单表数量是准确率的调节旋钮——D15 一旦评估不达标，从 120 张收到 40 张核心表，准确率通常能立刻上一个台阶。

07

我的核心模块：拆解与交接点

作为架构负责人，你要写的是「切开就会烂」的那几块——它们内部耦合紧、接口决定全局、返工成本最高。其余一切都应该交出去。

模块工期为什么必须你写交接点
仓库骨架与两层边界D1–D2harness/app 的单向依赖一旦第一周没立住，第三周就再也拆不开了D2 起所有人在此骨架上提交
协议与数据模型D2–D3它同时约束前端、后端、未来能否换回官方前端。改一次全员返工D3 交付 mock 流后完全交给前端，你不再碰前端
编排引擎D5–D7ThreadState + agent 循环 + 工具注册表 + StreamBridge 四者高度耦合，两个人写必然打架D7 后工具作者只需实现 Tool 基类，不碰引擎
ModelProvider 与 run 生命周期D8–D9紧贴编排引擎，且决定 token 计量与失败重试语义D9 后配置化，换模型不改代码
SqlDialect 抽象D10–D11决定未来接 StarRocks 是填空还是重写，是「架构同构」承诺的兑现点D11 后方言实现交给后端 A 扩展
Prompt 工程D13–D18准确率的最终责任人；它需要同时懂编排、懂工具、懂业务口径——只有你三样都有不交接，持续到冻结日
你最该警惕的三件事

① 不要去写工具实现。search_tables、run_sql 这些看着最有意思，但它们是可并行、可替换的叶子节点，交给后端 A。你一旦下沉去写工具，编排引擎就会晚，全队跟着堵在 D7。

② 不要碰前端。你「全栈都懂」是这个项目最危险的属性。协议交付后前端就是黑盒，你的时间不该花在那里。

③ 不要自己做部署。K8s + CI/CD 明确指给后端 B 或第 5 人。这块延期只影响 D17–D18，不在关键路径上；而你延期，整个项目延期。

按「杀死项目的能力」排序，不按发生概率排序。前三条都不是技术问题。

#风险等级触发信号应对

R3拿不到黄金测试集高 D2 挖不到历史 SQL 日志；D4 约不到业务方 假设 A2 的直接后果。降级方案：每周一次业务方试用会替代自动回归，但必须同时告知验收方「本项目将没有客观准确率指标」——这是必须上报的决策，不能默默承受

R5前端流式状态管理中高 D8 仍无法稳定渲染 tool_call 中间态；断线重连丢消息 Vue 自研且无参考实现。缓解已排进计划：D3 冻结协议 + mock 流先行。兜底：降级为「非流式，整轮返回」，体验变差但功能完整，改动约 1 天
R6元数据质量不均中 注释覆盖 80% 但存在同名不同义的表、口径分歧 覆盖率不等于口径清楚。表卡片的 metrics_note 字段就是为此存在。D13–D14 按评测归因定向补，不追求全量补齐

R8模型 token 成本失控低 单次问答超过 3 万 token 架构上已规避：search_tables 只返回摘要，describe_table 按需展开。加一条 run 级 token 上限告警即可
R9单副本可用性低 Pod 重启导致正在跑的问答丢失 已接受。启动回收 interrupted + 前端「重试」按钮。取数问答是短任务，重试成本远低于 checkpoint 续跑的实现成本
09

从 MVP 到完整版

五个增量，每个都是在既有骨架上填空。顺序按「投入产出比」排，不按 DeerFlow 的模块顺序排。

增量内容预估为什么排在这个位置
I1qa_samples 接成 few-shot 检索 + 用户反馈闭环2–3 周MVP 已经在攒数据，接上就见效。准确率提升通常大于换更大的模型——这是第一优先级，没有之一
I2StarRocks 方言 + 多数据源路由1–2 周SqlDialect 抽象已在，是纯填空。覆盖用户面最广
I3RBAC + 行级/表级数据权限 + 复用数仓自身权限3–4 周role / allowed_roles 字段已埋。用户规模一扩大，这条立刻从「可选」变成「阻塞」
I4沙箱 + Python 分析 + 分析报告生成4–6 周需要安全审批，周期不可控，所以放后面。ToolExecutor 抽象已在。这一步做完才能吃下 MVP 砍掉的场景 (b)
I5Skills / MCP / 子智能体 / IM 渠道 / 定时任务按需DeerFlow 2.0 的通用能力。它们让平台更「像 DeerFlow」，但对数据部门的直接业务价值最低，所以排最后。有明确需求再做，不要为了对标而做
对「后续演进到完整版」这句承诺的诚实说明

DeerFlow 2.0 是 15 万行非测试后端代码的体量，那是几十人年的积累。你们不会、也不需要「追平」它。这份 MVP 的骨架与它同构，意味着 I1–I5 每一步都是在既有分层里填空、而不是推倒重来——这已经是一个月的预算能买到的最好结果。真正决定这个产品价值的，是 I1 那条准确率飞轮，而不是 I5 里那些看起来更像「超级智能体」的功能。
