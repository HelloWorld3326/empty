未经确认的四个假设

A1 没有干系人明确要求「跑 Python 分析」→ 零沙箱写死，预留 3 人天的进程内 pandas 后处理预案。
A2 能拿到历史 SQL 日志 + 业务方派 1 人配合 2–3 天 → 黄金测试集成立。

方案一 · 数据 Agent 平台完整架构

这是数据 Agent 平台的目标形态——一个面向数据部门的通用智能体底座：单个主智能体编排工具、子智能体、持久记忆与沙箱执行，所有能力围绕数据资产展开。它不是一次性交付物，而是 MVP 之后逐步长成的终局。第 3 节的 MVP 是它的第一个可交付切片。

七条架构原则

这七条是平台从第一天就要立住的地基。它们不增加 MVP 的工作量，却决定了三个月后这套代码还能不能演进。

  • 框架层与应用层单向依赖，并用 CI 测试强制。这是让「框架」不被业务代码腐蚀的唯一有效手段——靠自觉守不住。
  • 单一状态载体：一次会话的全部状态收敛到一个状态对象，所有中间件读写同一份，禁止各自藏私有状态。
  • 中间件链：把「模型调用前要做的事」拆成有序可插拔的段，而不是塞进一个不断膨胀的函数。
  • 工具多源装配：内置工具、配置化工具、外部协议工具由统一注册表装配，新增工具不改引擎。
  • 流式双通道：既发增量，也周期性发有界快照。增量丢包时前端靠快照对齐，不必重连整轮。
  • 配置分权：会导致代码加载的配置项只能由运维掌管，绝不放进接口可写的配置文件。
  • 入口最小暴露：只有网关对外，内部服务端口一律不发布，并由 CI 校验部署清单。
关于「完整架构」的诚实预期

上图是终局，不是一个月能建成的东西。同类平台的完整形态通常意味着十万行量级的后端代码与多年演进。这份蓝图真正的价值在于：MVP 的骨架与它同构，因此后续每一个子系统都是在既有分层里填空，而不是推倒重来。第 9 节给出了从 MVP 走到这里的五个增量。

Agent 的六个工具

MVP 只有一个 lead agent，它能调用的工具就是产品能力的全集。工具越少、边界越清楚，ReAct 循环越稳。

工具签名职责与约束
search_tables(query: str, top_k=8)在表卡片上做检索，返回候选表的摘要卡片（表名/中文名/业务域/一句话用途）。只在白名单内检索
describe_table(table: str)返回完整 schema：字段名、类型、中文注释、示例值、常用口径、关联表提示
search_knowledge(query: str, top_k=5)转发到公司向量库 API，返回口径文档片段 + 出处，供引用
run_sql(sql: str, datasource: str)校验 → 限流 → 执行 → 返回结果集。SELECT-only、白名单表校验、强制 LIMIT、语句超时、行数上限，全程审计
make_chart(spec: ChartSpec)只产出图表配置 JSON（类型 + x/y 字段 + 标题），不渲染、不跑代码，前端 ECharts 负责画
ask_clarification(question: str)口径歧义或缺少时间范围时反问用户，中断本轮等待输入
这一节最容易被忽略的设计

search_tables 与 describe_table 必须分成两个工具，不能合并成一个「给我所有表结构」。白名单 200 张表的完整 schema 塞进 prompt 会是几万 token，成本高且准确率反而下降。正确的形状是：先检索出 5–8 张候选表的摘要，agent 判断后只对 1–3 张展开完整结构。这是 Text-to-SQL 准确率和成本的关键分水岭。

部署形态

  • K8s Deployment replicas=1 + strategy: Recreate。单 Pod 内 uvicorn 多 worker 关闭（agent 状态在进程内），并发靠 asyncio。
  • 启动时把上次遗留的 running 运行标记为 interrupted，前端展示「已中断，可重试」。不做 checkpoint 续跑——取数问答是短任务，重试成本低于实现成本。
  • 配置：config.yaml 走 ConfigMap，数据源凭证与模型 API Key 走 Secret。
  • 前端静态产物由同一个 Pod 的 nginx sidecar 托管，或直接打进镜像——不为 MVP 单独开一个前端服务。
04

核心数据模型与 SSE 协议

这两样东西必须在 D4 之前冻结。它们是前后端并行开发的唯一前提，也是平台后续所有客户端（Web、IM 渠道、开放 API）共用的统一契约。

数据模型

前六张是平台通用的会话与运行模型，与业务无关；后四张是数据侧资产。

-- 平台通用：会话与运行模型 --------------------------------------
users        (id, username UNIQUE, password_hash, display_name, role, is_active, created_at)
threads      (id, user_id, title, created_at, updated_at, archived_at)
messages     (id, thread_id, role, content, created_at, seq)
             -- role: user | assistant | tool | system
runs         (id, thread_id, status, model, started_at, finished_at, error,
              input_tokens, output_tokens)
             -- status: queued | running | succeeded | failed | interrupted | cancelled
tool_calls   (id, run_id, message_id, tool_name, args JSONB, result JSONB,
              status, started_at, finished_at, error)
artifacts    (id, thread_id, run_id, kind, uri, meta JSONB, created_at)
             -- kind: table | chart | csv

-- 数据侧资产 --------------------------------------------------
datasources  (id, name, engine, dsn_secret_ref, is_active)
             -- engine: postgres | mysql   (starrocks 留给完整版)
table_cards  (id, datasource_id, schema_name, table_name, display_name_cn,
              business_domain, purpose, columns JSONB, sample_values JSONB,
              metrics_note, embedding_ref, reviewed_by, reviewed_at,
              allowed_roles TEXT[] DEFAULT '{*}')
             -- columns: [{name,type,comment_cn,nullable,is_sensitive}]
sql_audit    (id, user_id, thread_id, run_id, datasource_id, question,
              generated_sql, validated BOOL, reject_reason, executed BOOL,
              row_count, elapsed_ms, created_at)
qa_samples   (id, thread_id, question, final_sql, tables_used TEXT[],
              user_feedback, created_at)
             -- MVP 只写不读；完整版接成 few-shot 检索
为什么 sql_audit 单独成表

它不是 tool_calls 的冗余。tool_calls 服务于会话回放，字段随工具协议演化；sql_audit 服务于安全合规，字段必须稳定、必须能被 DBA 和安全团队直接查询、必须记录被拒绝的 SQL（那些根本没进 tool_calls）。这张表是团队面对合规质疑时唯一的挡箭牌，成本极低。

SSE 事件协议

单一 GET /api/threads/{tid}/runs/{rid}/stream，text/event-stream。事件名与平台五对象语义一一对应，字段收敛到最小集。

run.started        { run_id, thread_id, model }
message.delta      { message_id, delta }              # 助手文本增量
tool_call.started  { tool_call_id, tool_name, args }
tool_call.delta    { tool_call_id, stage, detail }     # 如 stage=validating|executing
tool_call.finished { tool_call_id, status, result_ref }
artifact.created   { artifact_id, kind, uri, meta }
state.snapshot     { messages_tail, tool_calls_open }  # 有界快照，每 N 秒一次
run.finished       { run_id, status, usage }
run.error          { run_id, code, message }
ping               { ts }                             # 15s 心跳，防中间层断流
  • 快照 + 增量双通道：增量丢包时前端可用 state.snapshot 对齐，不必重连整轮。
  • result_ref 而非内联结果：大结果集走 GET /api/artifacts/{id} 分页取，避免把上万行塞进 SSE。
  • 断线重连带 Last-Event-ID，服务端从 messages.seq 续发。
D3 必须交付

这份协议 + 上面的 DDL + 一个能吐假事件的 /mock/stream 端点。前端从 D4 起就靠 mock 流开发，不等后端。这是整个排期里最重要的一次解耦——没有它，前端会空转到第二周。

Text-to-SQL样本飞轮 + 多轮自纠错 + 口径仲裁简化检索 → 生成 → 校验 → 执行 → 解读，单轮。填空

可视化图表推荐 + 看板沉淀 + 定时推送简化LLM 出 chart spec，前端 ECharts 渲染。填空

统计口径：MVP 相对完整形态，完全砍掉 8 个子系统、简化 15 个、保持 2 个。演进路径一列里没有一项是「重写」，全部是「填空」——这是这份 MVP 架构唯一需要被验证的指标，也是它区别于「先做个能跑的demo，回头再重构」的地方。

20 个工作日任务规划

3 人配置：架构（应用层 + 数据能力 + 交付）、算法（框架层 harness + 提示词）、前端（Vue 工作台）。相比 4 人基线少了整整一条泳道，因此这一节先给范围削减清单，再给排期——不砍范围，后面的日程是假的。

分工原则

三个人的切法只有一条硬规则：耦合最紧的东西必须落在同一个人手里，跨人的地方必须是稳定契约。据此把系统切成两块半：

算法 · 框架层

智能体循环、状态对象、流式桥接、模型接入、提示词。这五样互相咬合，且都围绕「模型怎么被驱动」这一个问题，交给同一个人。

架构 · 应用层与数据能力

网关、认证、审计、持久化、元数据、SQL 校验与执行、工具实现、评测、部署。围绕「数据怎么被安全地拿到」这一个问题。

前端 · 工作台

靠 D3 冻结的 SSE 协议与后端完全解耦，全程不依赖后端进度。

这个切法的代价，必须提前认

4 人方案里，编排引擎和应用层都在架构一个人手上——接口定错了自己改就行。现在这条边界横在两个人之间，接口错误的修复成本从「改代码」变成「开会 + 改两边」。所以 D1–D3 必须由架构与算法共同把三件事定死：RunManager 对应用层暴露的方法签名、SSE 事件类型全集、Tool 基类的入参出参约定。这三样定完之前，两个人不要各自往下写。

范围削减清单

人力少了 25%，范围必须同步收。下面七项是我建议直接从 MVP 拿掉的，合计省下约 16 人天，正好补上缺失那条泳道的大部分缺口。

三条泳道的边界与交接点

跨人的地方只有三处接口。把它们写清楚，三个人就能各自闷头写；写不清楚，每天都要开会。

归属拥有什么对外只暴露不碰什么
算法
框架层		 ThreadState、agent 循环、StreamBridge、工具注册表、ModelProvider、提示词 RunManager.start_run() / cancel()、事件流、Tool 基类 工具的业务实现、SQL、元数据、任何应用层代码
架构
应用层 + 数据		 网关与路由、认证、审计、持久化、元数据与表卡片、SQL 校验与执行、四个数据工具、评测、部署 REST API + SSE 事件（对前端）、四个工具实现（对框架层） agent 循环内部、提示词内容
前端
工作台		 Vue 工作台全部页面与状态管理、ECharts 渲染 — 后端任何代码；只认 D3 冻结的协议

三处接口，D3 必须定死

接口谁定定不清楚会怎样
SSE 事件全集架构主笔，算法确认可实现前端与框架层对同一个事件的理解不一致，D10 集成日当场返工。这是三处里最贵的一处
Tool 基类约定算法主笔，架构确认可实现入参校验放在哪一侧、错误怎么回传、结果多大要走引用——不定清楚，四个工具写完要重写
RunManager 方法签名两人共定应用层无法在框架层没写完时先跑起来，D5–D9 的并行就不成立
三个角色各自最该警惕的一件事

架构：不要去写框架层。你现在的活比 4 人方案时更多而不是更少——应用层、数据侧、评测、部署四块全在你手上。一旦下场帮算法写循环，D9 的两条泳道会同时晚。

算法：不要把业务逻辑写进提示词以外的地方。「这张表要不要过滤测试数据」这类判断属于工具实现，属于架构那侧。写进框架层，未来做别的智能体时整块没法复用。

前端：不要等后端。D3 拿到 mock 流之后，到 D9 之前完全不需要真实后端。一旦养成「等接口」的习惯，前端会成为第二条关键路径。

从 MVP 到完整版

五个增量，每个都是在既有骨架上填空。顺序按「投入产出比」排，不按架构图的模块顺序排。

增量内容预估为什么排在这个位置
I1qa_samples 接成 few-shot 检索 + 用户反馈闭环2–3 周MVP 已经在攒数据，接上就见效。准确率提升通常大于换更大的模型——这是第一优先级，没有之一
I2StarRocks 方言 + 多数据源路由1–2 周SqlDialect 抽象已在，是纯填空。覆盖用户面最广
I3RBAC + 行级/表级数据权限 + 复用数仓自身权限3–4 周role / allowed_roles 字段已埋。用户规模一扩大，这条立刻从「可选」变成「阻塞」
I4沙箱 + Python 分析 + 分析报告生成4–6 周需要安全审批，周期不可控，所以放后面。ToolExecutor 抽象已在。这一步做完才能吃下 MVP 砍掉的场景 (b)
I5技能包 / 外部工具协议 / 子智能体 / IM 渠道 / 定时任务按需平台的通用底座能力。它们让平台更「像一个通用智能体平台」，但对数据部门的直接业务价值最低，所以排最后。有明确需求再做，不要为了架构完整性而做
对「后续演进到完整版」这句承诺的诚实说明

第 2 节那张完整架构图是终局，不是一个季度能建成的东西。不需要、也不应该急于追平它。MVP 的骨架与它同构，意味着 I1–I5 每一步都是在既有分层里填空、而不是推倒重来——这已经是一个月的预算能买到的最好结果。真正决定这个产品价值的，是 I1 那条准确率飞轮，而不是 I5 里那些看起来更像「通用智能体平台」的功能。
