一期做智能体的创建、配置、发布、管理与问答；资源中心只做模型、MCP/API 工具、Skill、知识库（外部）四类。

后端与算法产能充足，前端是唯一瓶颈：需求 46.5 人天，1 人 4 周只有 20 人天，缺口 26.5 人天。而在 4 人 4 周档位下后端反而会因为前端做不完而闲置——这正说明补前端是全局最高杠杆的一笔投入。

建议按 5 人 5 周立项（+1 前端 +1 周）。若人力不批，按 P0 交付并对外明确定义为"内部验证版"，不承诺试用。

关于估算口径

本文所有人天已按「AI 让编码环节提速 2.5–3 倍、设计与联调环节不变」折算。AI 压缩的是敲代码，压不动对齐、联调、拿权限、验收、改需求——在一个 4 周、大量对接内部系统的项目里，后者占比超过一半。

以「模型管理」这一个切片为例，人工 5 人天 → AI 辅助 1.9 人天（提速 2.6 倍），其中「拿到真实 key 跑通 + 异常路径验收」那 0.7 人天完全压不动。任何按「AI 提速 10 倍」排的计划都会崩。

§03

运行机制

SSE 事件协议

思考过程、工具调用、引用来源是独立事件流而非最后一次性返回——原型图里「思考过程实时展开」「引用数量实时累加」的交互依赖这一点。前端 mock server 也基于这份协议造假数据，因此前端在第 2 天就能开发问答页。

event: run.started      { run_id, agent_id, version_no, mode }
event: thinking.step    { step_id, phase: "识别"|"检索"|"调用", text }
event: tool.call        { call_id, tool_name, tool_type, args_summary }
event: tool.result      { call_id, status, duration_ms, summary }
event: citation         { citation_id, source_type, source_name, title, snippet }
event: message.delta    { text }
event: message.done     { message_id, finish_reason, duration_ms }
event: run.error        { code, message }
event: run.cancelled    { reason }

配置快照如何变成可执行 agent

AgentAssembler 从 agent.config JSONB 读取快照，组装出四样东西：

  1. system prompt = 用户填的 Prompt + 挂载 Skill 的模板体（按输入变量渲染）+ 输出格式约束
  2. 工具清单 = 挂载的 MCP 工具（resource_mcp_tool.input_schema 转 function calling schema）+ 内置知识检索工具（若挂载了知识库）
  3. 模型参数 = model / max_tokens / temperature / top_p
  4. 上下文策略 = 自动压缩 / 阈值摘要 / 不压缩

§06

权限模型

三层，照搬 nexent：

  1. RBAC — sys_role_permission 表，role → (category, type, subtype)。控制「能不能进这个菜单、能不能调这类接口」。一期两个角色：ADMIN、USER。
  2. DAC — 资源级判定：输入 CurrentUser(user_id, tenant_id, role, groups) 与 Resource(created_by, group_ids, ingroup_permission)，输出 ResourceAccess(can_read, can_edit, is_creator)。
  3. tenant_scope — 所有查询自动注入 tenant_id 过滤（一期恒为同一值）。

与 PRD 四档可见范围的映射

PRD 可见范围本方案实现
仅自己ingroup_permission = PRIVATE
指定成员 / 指定部门group_ids = [...] + ingroup_permission = READ_ONLY
全员可见租户级 READ_ONLY

前端因此从「四档下拉 + 成员选择器 + 部门选择器」简化为「选组 + 选组内权限」，省 2 前端人天。

§07

任务拆解

不按「层」分工（后端 A 写 service、后端 B 写 controller），而按端到端垂直切片——一个切片从表到 API 到页面由一个 owner 负全责。在 AI 辅助模式下这是关键：AI 在单个完整切片里上下文最全、幻觉最少；按层分工会让两个人的 AI 各自幻觉出不兼容的接口。

「垂直切片」不等于「一个人写两种语言」

这一点容易误解：反对的是按技术层切任务，不是反对前后端分人。「负全责」指对结果负责，不是代码都得他一个人敲。25 个切片实际分三类，分工方式不同：

类型切片分工
纯后端S0 S2 S4 S5 S6 S16一个人全做
纯前端S17 S18 S19一个人全做
前后端都有（16 个，占大头）S1 S3 S7–S15 S20–S24一前一后配对，指定一个 owner

对第三类的三条规则：

  1. 每个切片指定一个 owner（通常是后端那位）。契约完不完整、验收过没过、有分歧谁拍板，都是 owner 的事。
  2. 两人同时开工，不是接力。后端写接口的同时，前端基于 mock 写页面——这就是第一周做契约与 mock 的全部意义。
  3. 一起验收。验收标准由两人一起点一遍，不是各测各的。

用 AI 缓解前端缺口的一个用法

W1 由 FE2 建好组件基建（表格 / 弹窗 / 表单封装）之后，资源中心那几个页面基本是「填空」——列表 + 分页 + 搜索 + 新增弹窗 + 删除确认，没有复杂交互。这类页面后端同学用 AI 能写出来，前端只做 review。

不做的范围

一期明确不做以下内容，需求变更须重新评估排期。

来自 PRD 的裁剪

  • 工作台概览页及其全部首页能力
  • 全部统计卡片与指标（管理中智能体 / 本周调用 / 平均满意度 / 待发布 / 各资源统计）
  • 测试数据集与回归测试（第 6.11 节全章）
  • 数据资源：数据源 / 数据表 / 报表（第 6.10 节全章）
  • 语音输入（ASR）
  • 待处理详情、待发布详情等统计下钻交互

技术侧裁剪

  • NL2Agent（自然语言自动生成智能体配置）
  • Skill 的代码执行与沙箱（Skill 仅为 Prompt 模板）
  • 平台自建知识库（解析 / 切分 / embedding / 向量检索）
  • 多租户隔离逻辑（仅预留字段）
  • SSO / LDAP / CAS 对接（仅预留字段）
  • 版本回滚 UI（表结构支持，二期加按钮）
  • 任务队列与水平扩展（接口形状已预留）
  • A2A、长期记忆、配额计费、监控看板
