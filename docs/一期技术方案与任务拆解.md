# SUPCON 数据智能体平台 · 一期技术方案与任务拆解

> 版本 v1.0 · 2026-08-26 · 依据 PRD v0.1 与用户侧功能原型
> 参考项目：[nexent](https://github.com/ModelEngine-Group/nexent)（Apache-2.0）

## 0. 一句话结论

一期做**智能体的创建、配置、发布、管理与问答**，资源中心只做**模型 / MCP·API 工具 / Skill / 知识库（外部）**四类。
后端与算法产能充足，**前端是唯一瓶颈：需求 46.5 人天，1 人 4 周只有 20 人天。**
**建议按 5 人 5 周（+1 前端 +1 周）立项**；若人力不批，按 P0 交付并对外明确定义为"内部验证版"，不承诺试用。

## 1. 决策台账

所有决策已逐条确认。后续实现如需推翻，走变更流程并更新本表。

| # | 决策项 | 结论 | 关键后果 |
|---|---|---|---|
| D1 | 代码基线 | 自研后端 + vendored `nexent` SDK 作为 agent 运行时；用户体系抄表设计不抄 Supabase | 业务层完全自控，不继承 60 路由 / 80 服务的包袱 |
| D2 | NL2Agent（自然语言自动生成智能体） | **不做** | 配置页是纯人工配置，交互不分裂 |
| D3 | 资源中心范围 | 做：模型、MCP/API 工具、Skill、知识库（仅管理）<br>**砍**：数据资源、测试数据集、全部统计卡片 | 省掉一个完整产品（NL2SQL）与一整套向量库设施 |
| D4 | Skill 的本质 | **结构化 Prompt 模板**（名称 / 输入变量 / 输出格式 / 模板体），支持 AI 生成；不执行代码、不做沙箱 | 避开安全禁区；"健康状态"降级为"最近一次试运行结果" |
| D5 | 发布语义 | **快照式版本**：`version_no=0` 为草稿，`>=1` 为发布快照，`current_version_no` 指向当前线上版 | 编辑不影响线上；配置变更 diff 天然有来源；可回滚（表结构支持，UI 二期） |
| D6 | 执行模型 | FastAPI 进程内 asyncio；接口按队列形状设计：`POST /runs` → `GET /runs/{id}/stream` → `POST /runs/{id}/cancel` | 用单机的成本买可演进的接口，二期换队列前端零改动 |
| D7 | SSE 事件协议 | 9 类事件，思考过程 / 工具调用 / 引用来源均为**独立事件流** | 支撑原型图的实时展开交互 |
| D8 | 模型接入 | 阿里云百炼 OpenAI 兼容端点 + **标准 function calling**；不做 Embedding；**ASR 砍掉** | 不用 CodeAgent 范式，运行时预算 8→6 人天且稳定性大幅提升 |
| D9 | 知识库 | 外置。抽象 `KnowledgeProvider`（`list_kb` / `search` / `get_doc`），一期只实现内网适配器 | 内网接口不理想也不阻塞运行时开发 |
| D10 | 租户 | 单租户单实例；**全表预留 `tenant_id` 但不实现隔离逻辑** | 二期要隔离时不迁数据，当前成本为零 |
| D11 | 身份 | 一期自建账号密码（管理员建号）；`sys_user` 带 `external_id` / `source` 预留外挂身份源 | 不被 SSO 对接的外部排期绑架 |
| D12 | 权限模型 | **照搬 nexent**：RBAC + DAC + tenant_scope，资源可见性用 `created_by` + `group_ids` + `ingroup_permission ∈ {PRIVATE, READ_ONLY, EDIT}` | 替代 PRD 的四档可见范围，前端选择器简化，省 2 前端人天 |
| D13 | 前端栈 | Vue3 + Vite + **TypeScript** + Pinia + **Ant Design Vue** + pnpm | nexent 前端代码**一行不可复用**，仅作交互参考；流式渲染 / trace / 引用面板需自建，+3 人天 |
| D14 | 后端栈 | Python 3.11 + FastAPI + SQLAlchemy 2 + **PostgreSQL**（JSONB 存配置快照）+ Redis | 一期**不引入** Elasticsearch / MinIO / 向量库 / Celery |
| D15 | 仓库结构 | monorepo：`/contracts` `/backend` `/agent-runtime` `/frontend` | OpenAPI spec 单一真源，契约改动全员立刻可见 |
| D16 | 协作模式 | **契约先行 + mock 驱动**：第 1 周只产出 schema / spec / SSE 协议 / mock server；之后按**垂直切片**分工 | 前端从第 2 天满负荷，零等待后端；TS 类型由 spec 生成，挡住 AI 的字段名幻觉 |
| D17 | 算法分工 | W1–W2 专职打通运行时最小可用版；W3–W4 转资源中心后端 + Skill 的 AI 生成 | 避免"运行时单点阻塞全组"，W2 末必须有可出流式回答的 endpoint |
| D18 | 附件 | 做。存本地卷 + `attachment` 表，**平台不解析文档**，超阈值只传文件名与摘要 | 不为附件引入 MinIO；长文档引导用户走知识库 |

### 关于估算口径

本文所有人天已按 **"AI 让编码环节提速 2.5–3 倍、设计与联调环节不变"** 折算。

AI 压缩的是敲代码，压不动**对齐、联调、拿权限、验收、改需求**——在一个 4 周、大量对接内部系统的项目里，后者占比超过一半。以"模型管理"切片为例：人工 5 人天 → AI 辅助 1.9 人天（提速 2.6 倍），其中"拿到真实 key 跑通 + 异常路径验收"那 0.7 人天完全压不动。任何按"AI 提速 10 倍"排的计划都会崩。

### 2.2 两条数据流

- **配置流**（同步 JSON）：前端 → API → 领域服务 → PostgreSQL。所有 CRUD、发布、挂载走这条。
- **运行流**（异步 SSE）：前端 `POST /runs` 拿 `run_id` → `GET /runs/{id}/stream` 建 SSE → RunManager 起 asyncio task → LLM 与工具多轮往返，每一步发事件 → 事件同时写 `run_event` 表用于回放。

**关键设计**：即时测试与正式问答**共用同一条运行流**，区别仅在 `run.mode = test | chat`——test 模式不写 `conversation` / `message`，只写 `run` 与 `run_event`。这让"即时测试"这个切片的边际成本接近零。

### 2.3 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端框架 | Vue3 + Vite + TS | 团队背景；TS 承接 spec 生成的类型 |
| 组件库 | Ant Design Vue | 原型图视觉语言即 Ant，Table/Modal/Form 一一对应 |
| 状态管理 | Pinia | Vue3 官方，轻 |
| 后端框架 | FastAPI | 原生 async，SSE 与 asyncio 取消天然契合 |
| ORM | SQLAlchemy 2.0 | 与 nexent 一致，表设计可直接迁移 |
| 数据库 | PostgreSQL 15+ | JSONB 存配置快照是核心便利 |
| 缓存 | Redis 7 | run 状态、取消标志、并发限流 |
| Agent 内核 | vendored nexent SDK | 复用 MCP 适配与流式封装 |
| LLM | 阿里云百炼 OpenAI 兼容 | 已有 key，支持 function calling |
| 契约 | OpenAPI 3.1 + Prism/msw mock | 单一真源，双端类型生成 |

**一期明确不引入**：Elasticsearch、MinIO、向量数据库、Celery/RabbitMQ、Kubernetes。

## 3. Agent 运行机制

### 3.1 SSE 事件协议

```
event: run.started      { run_id, agent_id, version_no, mode }
event: thinking.step    { step_id, phase: "识别"|"检索"|"调用", text }
event: tool.call        { call_id, tool_name, tool_type, args_summary }
event: tool.result      { call_id, status, duration_ms, summary }
event: citation         { citation_id, source_type, source_name, title, snippet }
event: message.delta    { text }
event: message.done     { message_id, finish_reason, duration_ms }
event: run.error        { code, message }
event: run.cancelled    { reason }
```

**要点**：思考过程、工具调用、引用来源是**独立事件流**而非最后一次性返回——原型图里"思考过程实时展开""引用数量实时累加"的交互依赖这一点。前端 mock server 也基于这份协议造假数据，因此前端在第 2 天就能开发问答页。

### 3.2 一次运行的时序

```
前端                API/RunManager        LLM(百炼)        工具
 │  POST /runs         │                    │              │
 │────────────────────>│  建 run 记录        │              │
 │<── { run_id } ──────│                    │              │
 │  GET /runs/{id}/stream                   │              │
 │────────────────────>│                    │              │
 │<══ run.started ═════│                    │              │
 │                     │ 组装快照配置        │              │
 │                     │ system prompt      │              │
 │                     │ + Skill 模板       │              │
 │                     │ + 工具 schema      │              │
 │<══ thinking.step ═══│───── chat ────────>│              │
 │                     │<── tool_calls ─────│              │
 │<══ tool.call ═══════│                    │              │
 │                     │──────── 调用 ─────────────────────>│
 │                     │<─────── 结果 ──────────────────────│
 │<══ tool.result ═════│                    │              │
 │<══ citation ════════│                    │              │
 │                     │───── chat ────────>│  (带工具结果) │
 │<══ message.delta ═══│<── stream tokens ──│              │
 │<══ message.done ════│  落库 run_event    │              │
 │                     │                    │              │
 │  POST /runs/{id}/cancel  ── 任意时刻 ──   │              │
 │────────────────────>│ 置 Redis 取消标志   │              │
 │<══ run.cancelled ═══│ cancel asyncio task│              │
```

取消的实现：`RunManager` 持有 `run_id → asyncio.Task` 映射，同时在 Redis 写 `run:{id}:cancel`。工具调用的每一轮循环开头检查标志位，LLM 流式读取时用 `task.cancel()`。**二期换成任务队列时，这三个 HTTP 接口的形状不变，前端一行不改。**

### 3.3 配置快照 → 可执行 agent

`AgentAssembler` 从 `agent` 表的 `config` JSONB 读取快照，组装出：

1. **system prompt** = 用户填的 Prompt + 挂载 Skill 的模板体（按输入变量渲染）+ 输出格式约束
2. **工具清单** = 挂载的 MCP 工具（从 `resource_mcp_tool.input_schema` 转 function calling schema）+ 内置的知识检索工具（如挂载了知识库）
3. **模型参数** = model / max_tokens / temperature / top_p
4. **上下文策略** = 自动压缩 / 阈值摘要 / 不压缩

## 4. 版本与发布模型

照搬 nexent 的 `(agent_id, version_no)` 复合主键设计——该设计已在生产项目验证。

```
agent 表  PK (agent_id, version_no)

  version_no = 0     ← 草稿行，创作者编辑的就是它
  version_no = 1     ← 第一次发布时拷贝草稿产生的快照（不可变）
  version_no = 2     ← 第二次发布的快照
  ...
  agent_meta.current_version_no = 2   ← 线上问答读这一版

动作与状态迁移：
  保存草稿   → 只改 version_no=0 那一行，status 不变
  发布       → 拷贝 0 → 新 version_no=N，current_version_no=N，status=已发布
  编辑已发布 → 只改 version_no=0，线上仍读 N；前端提示"有未发布变更"
  下架       → status=已下架，current_version_no 保留
  上架       → status=已发布
  删除       → 仅草稿 / 已下架可删；已发布必须先下架
```

**这是整份设计里最不愿妥协的一条。** 相比"单份配置 + 自增版本号"只多约 2 人天（一张表 + 前端一个未发布变更提示），但它决定了业务专家改坏一个字时线上会不会立刻挂——是玩具还是生产工具的分界。

**配置变更记录**由此天然获得数据源：diff `version_no=0` 与 `current_version_no` 的两份 JSONB 即可，不需要在每个写接口里埋点。

## 5. 数据模型

20 张表，按域分组。所有表带 `tenant_id`、`created_by`、`created_at`、`updated_at`、`deleted_at`（软删）。

| `sys_group` | `group_id` PK, `name`, `parent_id`, `tenant_id` |
| `sys_user_group` | `user_id`, `group_id` |
| `sys_role_permission` | `role`, `permission_category`, `permission_type`, `permission_subtype` |

### 智能体域

| 表 | 关键字段 |
|---|---|

### 会话与运行域

| 表 | 关键字段 |
|---|---|
| `conversation` | `id`, `title`, `agent_id`, `agent_version_no`, `user_id` |
| `message` | `id`, `conversation_id`, `role`, `content`, `run_id` |
| `run` | `id`, `conversation_id`(可空), `agent_id`, `version_no`, `user_id`, `mode`(test/chat), `status`(running/success/cancelled/failed), `duration_ms`, `error` |

`run_event` 是"可审计"要求（PRD 9.4）的落点：对话详情弹窗直接按 `seq` 回放事件流，不需要额外的快照表。

## 6. 权限模型

三层，照搬 nexent：

1. **RBAC** — `sys_role_permission` 表，`role → (category, type, subtype)`。控制"能不能进这个菜单、能不能调这类接口"。一期两个角色：`ADMIN`、`USER`。
2. **DAC** — 资源级判定，输入 `CurrentUser(user_id, tenant_id, role, groups)` 与 `Resource(created_by, group_ids, ingroup_permission)`，输出 `ResourceAccess(can_read, can_edit, is_creator)`。
3. **tenant_scope** — 所有查询自动注入 `tenant_id` 过滤（一期恒为同一值）。

### 与 PRD 四档可见范围的映射

| PRD 可见范围 | 本方案实现 |
|---|---|
| 仅自己 | `ingroup_permission = PRIVATE` |
| 指定成员 / 指定部门 | `group_ids = [...]` + `ingroup_permission = READ_ONLY` |
| 全员可见 | 租户级 `READ_ONLY` |

前端因此从"四档下拉 + 成员选择器 + 部门选择器"简化为"选组 + 选组内权限"，省 2 前端人天。

## 7. 任务拆解（垂直切片）

**拆解原则**：不按"层"分工（后端 A 写 service、后端 B 写 controller），而按**端到端垂直切片**分工——一个人从表到 API 到页面完整拿下一个切片。在 AI 辅助模式下这是关键：AI 在单个完整切片里上下文最全、幻觉最少；而按层分工会让两个人的 AI 各自幻觉出不兼容的接口。

单位：人天。FE=前端，BE=后端，AL=算法。

| ID | 切片 | FE | BE | AL | 依赖 | 档位 |
|---|---|---|---|---|---|---|
| S0 | 契约先行：DDL / OpenAPI / SSE 协议 / mock server | — | 3 | — | — | P0 |
| S1 | 工程脚手架、CI、部署基线、鉴权中间件 | 2 | 3 | — | S0 | P0 |
| S2 | 身份与权限（RBAC + DAC + tenant_scope） | — | 4 | — | S1 | P0 |
| S3 | 登录与用户/组管理 | 3 | 2 | — | S2 | P0 |
| S4 | **Runtime M1**：单轮对话 + 流式 + 取消 | — | — | 6 | S1 | P0 |
| S5 | Runtime 工具层：MCP 客户端 / 知识检索工具 / Skill 注入 | — | 2 | 3 | S4,S13,S15 | P0/P1 |

## 8. 人力档位矩阵

| | 前端需求 | 前端产能 | 后端+算法需求 | 后端+算法产能 | 结论 |
|---|---|---|---|---|---|
| **4 人 4 周** | 46.5 | **20** | 61 | 60 | 前端缺 26.5，后端零缓冲 |
| **5 人 4 周**（+1 FE） | 46.5 | 40 | 61 | 60 | 前端缺 6.5，后端零缓冲 |
| **5 人 5 周**（+1 FE +1 周） | 46.5 | 50 | 61 | 75 | ✅ 两侧均有缓冲 |

**注意一个反直觉的事实**：在 4 人 4 周档位下，后端会因为前端做不完而**闲置**——后端 P0 只需约 39 人天，产能 60。这正说明"补前端"是全局最高杠杆的一笔投入，一个前端换来的产出远大于一个后端。

### 各档位交付内容

**P0 · 4 人 4 周 · 内部验证版**
登录与用户管理、智能体列表与状态机、配置页全套、即时测试（含流式回答）、资源·模型、资源·MCP/API。
**没有问答页、没有 Skill、没有知识库、没有记录追溯、没有附件。**
定位：验证"创建—配置—测试—发布"主链路可行，不对外承诺试用。

**P1 · 5 人 4 周 · 功能完整版**
P0 + 完整问答页（历史会话、引用面板、工具调用、反馈）+ 资源·Skill（含 AI 生成）+ 资源·知识库 + 附件上传。
**仍缺记录追溯**，PRD 第 9.4 节的可审计要求全部落空。

**P2 · 5 人 5 周 · 可试用版**（推荐）
P1 + 智能体记录三个 tab 与对话详情 + 发布前检查完整化 + 权限矩阵验证 + 异常路径与性能收敛 + 目标环境部署。
定位：可交给 3–5 个真实业务场景的业务专家自建自用。
